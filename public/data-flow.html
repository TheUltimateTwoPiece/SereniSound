SereniSound · Innofest

End-to-end data flow — ESP32 ⇄ caregiver app

One device (pwd-001) hardcoded in the firmware and in four API routes. The wearable is a sensor and actuator only: it never touches the database, never learns about geofences or heart-rate limits, and is never contacted by the server. Four flows exist — upload, command pull, realtime push, and outbound alert.

01System topology

Every hop, both directions. Numbers match the legend below the diagram.

1ESP32 → Vercel · POST /api/device/update — every 5 000 ms, or immediately when any state changes. JSON body, auth X-Device-Token. TLS via WiFiClientSecure + setInsecure() — no certificate validation. 6 s client timeout; on a non-200 the device retries in ~1 s instead of 5 s.
2Vercel → Supabase · upsert device_status — service-role key bypasses RLS, onConflict: device_id, stamps updated_at. The whole payload is validated first; address is truncated to 500 chars.
3Supabase → Browser · Realtime push (WSS) — postgres_changes on public.device_status filtered device_id=eq.pwd-001, listening for INSERT and UPDATE. Possible because the table is REPLICA IDENTITY FULL and a member of the supabase_realtime publication.
4Browser → Vercel · GET /api/device/status — every 5 000 ms with cache: no-store. This is the baseline path and the fallback whenever Realtime drops, so the dashboard keeps updating either way.
5Wearable ↔ Google · WPS + reverse geocode — the device talks to Google itself. POST geolocation/v1/geolocate with up to 12 scanned APs (RSSI ≥ −85 dBm), only while GPS has no fresh lock, at most every 30 s. GET geocode/json at most every 30 s and only if it moved ≥ 20 m. Neither is proxied by the app.
6Vercel → Brevo · alert email — runs inside after(), i.e. only once the device's response has been flushed. HTTPS API preferred (api-key header; rejects xsmtpsib- keys), otherwise SMTP smtp-relay.brevo.com:587 with requireTLS.
7Browser → Vercel · POST /api/device/command — same-origin gate, then a queue insert. Returns {success, command_id}. Nothing happens on the device yet: the dashboard has only queued work.
8Vercel ↔ Supabase · device_commands — INSERT as pending; read the oldest pending row via device_commands_pending_idx; UPDATE to delivered with delivered_at. Read-then-claim, not atomic, and there is no expiry and no acknowledgement.
9Wearable ↔ Vercel · GET /api/device/command — every 2 000 ms, skipped when a command is already in flight or Wi-Fi is down. 8 s client timeout; −11 means HTTPClient read timeout. This interval is what sets worst-case command latency.
10Browser → Vercel · GET|POST /api/alerts/settings — GET on load and every 15 000 ms, returning settings plus the last 20 alerts; POST saves the caregiver form. This is how alert history reaches the dashboard, since device_alerts is not a Realtime table.
11Brevo → caregiver inbox — inline HTML plus plain text, X-SereniSound-Alert header, X-Priority: 1 on warnings, all timestamps rendered in Asia/Singapore. Every interpolation is HTML-escaped.

02aInside the wearable — the two cores

The split exists because HTTPS and Wi-Fi scans block for hundreds of milliseconds; on one core that made the buttons feel dead.

02bCross-core state, peripherals, and the power machine

The only things that cross between cores are a handful of volatile globals, swapped under an interrupt lock.

03Data model

Four tables, all with RLS enabled. Only device_status is readable by a browser key, and only device_status is a Realtime table.

04aSequence — caregiver taps “Next track”

Solid = request, dashed = response. Total latency is dominated by the device's 2 s poll interval.

04bSequence — safety-zone breach through to email

The device is answered first; detection and delivery happen inside after(), so mail latency never touches the wearable's 5 s loop.
