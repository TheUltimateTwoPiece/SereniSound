SereniSound / Innofest

How data moves between the ESP32 and the caregiver app

There is one device, pwd-001, and its id is hardcoded in the firmware and in four API routes. The wearable only collects readings and acts on commands. It never opens a database connection, it has no idea what a geofence or a heart-rate limit is, and the server has no way to contact it. It does two things on the network: it pushes its state up, and it asks whether anything is waiting for it.

01System topology

Each numbered step is explained below the diagram.

1ESP32 to Vercel, POST /api/device/update. Sent every 5 seconds, or straight away whenever any state changes. The body is JSON and the request carries an X-Device-Token header. The firmware uses WiFiClientSecure with setInsecure(), so certificates are not validated. The client timeout is 6 seconds, and after a failure the device retries about a second later rather than waiting out the full interval.
2Vercel to Supabase, upserting device_status. The service-role key bypasses RLS, the upsert conflicts on device_id, and updated_at is stamped on the server. The payload is validated before any of this runs, and address is cut to 500 characters.
3Supabase to the browser, over a Realtime websocket. The client subscribes to postgres_changes on public.device_status, filtered to device_id=eq.pwd-001, and listens for both INSERT and UPDATE. This works because the table is REPLICA IDENTITY FULL and belongs to the supabase_realtime publication.
4Browser to Vercel, GET /api/device/status. Polled every 5 seconds with cache: no-store. This is the baseline, and also the fallback, so the dashboard keeps updating even when the websocket drops.
5The device and Google, for WPS and reverse geocoding. The wearable calls Google directly rather than going through the app. It posts up to 12 scanned access points to geolocation/v1/geolocate, only while GPS has no recent lock and at most every 30 seconds, and it calls geocode/json at most every 30 seconds and only after moving 20 m or more.
6Vercel to Brevo, sending the alert email. This runs inside after(), so it only starts once the device's response has been flushed. Delivery prefers the HTTPS API with an api-key header, and rejects xsmtpsib- keys outright, falling back to SMTP at smtp-relay.brevo.com:587 with requireTLS.
7Browser to Vercel, POST /api/device/command. A same-origin check runs first, then the command is queued as a row. The response is {success, command_id}. Nothing has happened on the device yet, because the dashboard has only queued work.
8Vercel and Supabase, over device_commands. Rows are inserted as pending, read back oldest-first through device_commands_pending_idx, then updated to delivered with a delivered_at stamp. That is a read followed by a claim rather than one atomic step, and there is no expiry and no acknowledgement.
9The device and Vercel, GET /api/device/command. Polled every 2 seconds, and skipped entirely while a command is already in flight or Wi-Fi is down. The client timeout is 8 seconds, and a return of −11 means an HTTPClient read timeout. This interval decides the worst-case command latency.
10Browser to Vercel, GET and POST /api/alerts/settings. GET runs on load and then every 15 seconds, returning the settings plus the last 20 alerts. POST saves the caregiver's form. This is also how alert history reaches the dashboard, because device_alerts is not a Realtime table.
11Brevo to the caregiver's inbox. Each message carries inline HTML and a plain-text part, an X-SereniSound-Alert header, and X-Priority: 1 on warnings. Timestamps are formatted for Asia/Singapore, and every value inserted into the HTML is escaped.

02aInside the wearable: the two cores

The firmware splits its work across both cores because HTTPS calls and Wi-Fi scans block for hundreds of milliseconds. When they ran on one core, the buttons felt unresponsive.

02bCross-core state, peripherals, and the power machine

Only a few values cross between the cores, and all of them are volatile globals swapped under an interrupt lock.

03Data model

Four tables, all with RLS switched on. A browser key can read device_status and nothing else, and device_status is the only table wired into Realtime.

04aSequence: a caregiver taps “Next track”

Solid lines are requests, dashed lines are responses. Most of the total delay is the device's 2 s poll interval.

04bSequence: a safety-zone breach reaches the inbox

The device gets its answer first. Detection and email happen inside after(), so a slow mail server never holds up the wearable's 5 s loop.
